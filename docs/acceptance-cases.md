# Behavioral acceptance cases

Expected results distinguish the ChatGPT planning session from the separate implementation session. Review actual generated prompts against these cases; static checks alone do not prove live host behavior or account installation.

| Input or situation | Expected result |
|---|---|
| `zdev` rough request | Complete grounded standalone prompt plus necessary artifacts; the planning Chat and its helpers perform only read-only GitHub research and initiate no GitHub-write approval requests. |
| Focused implementation task | Prompt directs the implementing agent to inspect state, reuse or create one tracker, and then implement. It includes accepted requirements, acceptance criteria and verification. |
| Multiple independently completable tasks | Prompt directs creation or reuse of a parent epic and linked sub-issues before implementation, with dependencies, concrete criteria, parent/child links and progress tracking. |
| Matching tracker, epic or children already exist | Read their scope and state, reuse appropriate records and create only missing ones. Preserve existing history and original issues. |
| Resume after compaction or uncertain issue-creation response | Recover canonical URLs and inspect existing records before retrying; do not create duplicate trackers or children. |
| Issue operations already requested by the execution prompt | No generic additional confirmation step for those in-scope writes; actual tool access controls and repository policy still apply. |
| User expressly forbids new issues across implementation | Carry that restriction forward, reuse permitted existing tracking, and adapt the default template so it grants no conflicting creation authority. |
| GitHub issue write unavailable | Preserve the proposed issue content and task mapping, report the exact failed operation or missing access, and continue independent authorized work without claiming the issue exists. |
| Meaningful implementation milestone or change of approach | Record findings, decisions, progress, verification commands/results with relevant revisions, PR links, blockers and next actions in the issues; keep parent and children consistent. |
| Pausing or handing off unfinished work | Update the issues with enough durable context for another session to resume without the originating Chat or private skill. |
| Generated prompt for Codex or Claude Code, local or cloud | Inline the complete execution procedure and preserve the specified environment. Include no plugin invocation, app link, raw planning flag or instruction about the planning Chat's permissions. |
| `zdev -m -is for https://github.com/zudolab/zudo-text` | Bulk sweep checkpoint; prompt translates accepted task groups and conditional merge intent into plain actions. No deployment or release authority. |
| `zdev -isask -is -pr -m` | Interview wins, accepted UI topics prototype after triage, and effective scope and lifecycle become plain instructions in the prompt. |
| `zdev -cccp ...` or `zdev - cccp ...` | Target Claude Code Cloud Project manager/child execution; normalize the spaced spelling. Do not infer a sweep, continuous loop or merge permission. |
| No environment flag or prose constraint; portable parser bug | Keep the prompt portable and explicitly say it can run in any supported environment. Expand all six supported environment names in the standalone prompt, without choosing the planning host by default. |
| No environment flag; mandatory Mac confirmation and a Claude Code preference | Select Claude Code local CLI on Mac from the task requirements and preference. Preserve the actual native acceptance requirement; the host name alone does not prove that the necessary capability is available. |
| `-coc`, `-cowsl`, `-comac`, `-ccwsl` or `-ccmac` supplied alone | Respect, respectively, Codex Cloud, Codex local CLI on WSL, Codex local CLI on Mac, Claude Code local CLI on WSL or Claude Code local CLI on Mac as a hard allowed scope. Include only tasks whose implementation and required acceptance can finish there. |
| `zdev -cowsl -a -m` with a portable bug and an inseparable native Mac bug | Execute the portable work and exclude the Mac bug from executable scope before assignment or implementation. Record its original issue, mandatory Mac requirement and suitable host separately from decisions; do not implement it on WSL with mandatory acceptance deferred. Apply the same filter on every later wave and preserve conditional merge gates. |
| Portable normalizer fix is independently useful but is also a prerequisite for a larger native Mac integration | Include the portable slice only with its own complete acceptance criteria and explicit boundary. Keep the larger Mac-dependent issue open and excluded from a WSL-only batch. Do not disguise an inseparable acceptance gap as a portable slice. |
| `zdev -cccp -comac -a` with mandatory Mac acceptance | Treat the flags as an allowed set, select Codex local CLI on Mac, and use its local subagents if available. Do not inject Project child-session instructions merely because Project was a candidate. |
| `zdev -coc -ccwsl` for only an inseparable Mac-required task | Report no compatible executable scope, with the original issue, unmet requirement and suitable Mac environment. Do not choose an unlisted Mac host or invent replacement work. |
| `zdev -coc -coc` or reversed order of several environment flags | Deduplicate the allowed set and select from requirements. Repetition and argument order do not create workers, change priority or require execution on every listed host. |
| Explicit prose says WSL only, with no environment flag | Honor the prose constraint, select a compatible WSL CLI and exclude incompatible native Mac work. Neither the current host nor the absence of a flag expands permission. |
| Multiple allowed environments are available but one can complete all accepted tasks | Prefer that sufficient environment. Use different allowed hosts for independent tasks only when needed, with explicit task boundaries and handoffs. |
| A WSL task reveals an inseparable Mac requirement after a partial local draft | Checkpoint the actual partial changes and evidence, stop further assignment or implementation of that incompatible task, keep its issue and acceptance open, and continue independent compatible work. Do not switch hosts outside the allowed set or close the task based on partial tests. |
| Selected Mac environment lacks a required physical Japanese IME setup | Record an actual physical-verification blocker and exact next action; do not call it a product decision or passed acceptance. Continue compatible independent tasks and retain the incomplete delivery issue. |
| Existing CI includes Mac jobs while the allowed execution set is WSL only | Run legitimate repository gates when authorized, but do not treat CI as an added execution destination or substitute for required real native or physical confirmation. Inseparable incompatible work stays excluded. |
| `zdev -coc -a` with portable bugs | Produce the same continuous sweep/development policy as other environments, using only actual Codex Cloud workers. Do not require Project or local CLI subagent APIs. |
| `zdev -ccwsl -a` with a substantive parser topic spanning several files and related issues | Assign one coherent topic to one local subagent when supported, with outcome, owned paths, dependencies and criteria. Let it investigate, plan, implement, self-review and run focused tests; reuse it for follow-ups and corrections. Do not fragment it per file or small command. |
| A local topic contains independent outcomes or conflicting ownership/capability needs | Split at those meaningful boundaries, or when the topic is unmanageably broad; serialize shared-file work. The parent owns queue and ownership coordination, cross-topic decisions, integration, independent review and final acceptance, following the repository's commit/push policy. |
| User describes Opus medium or Astra low as suitable topic workers | Treat these as illustrative capability/effort guidance. Preserve the selected or configured model and effort, discover supported names and controls, and do not invent model IDs or silently override settings. |
| Local CLI has no subagent support | Continue sequentially in the parent with the same scope, acceptance and continuous-loop rules. Do not invent worker APIs or drop the requested continuing work. |
| `zdev -a ...` | Inventory all open issues and PRs, reconcile comments/recent merges with source, present the first ready wave and a continuous-loop handoff without a redundant bulk approval. Do not infer a Project host or merge permission. |
| `zdev -cccp -a -m ...` | Manager-led Project team repeats inspect/plan/develop/review/verify/conditionally integrate/resweep, with bounded child ownership and actual repository rules; every merge still needs its gates. |
| `zdev -cccp -a ...` without merge authority | Continue independent ready tasks; retain implementation PRs and delivery issues open pending integration, without duplicating work or silently relying on unmerged changes. |
| `zdev -a -is ...` | Continuous mode supplies routine in-scope acceptance; no extra bulk checkpoint. Preserve existing no-auto restrictions and other holds. |
| `zdev -a -isask -pr ...` | Explicit interview wins; unaccepted candidates stay held and selected UI prototypes require acceptance. Continue only accepted independent work. |
| Open issue whose proposed fix already landed | Inspect comments, source and merge evidence; plan remaining verification or a reproduced residual defect, not another copy of the landed implementation. |
| New reproducible defect found during a continuous batch | Search/reuse tracking, add it to the accepted repository-scoped queue with evidence and criteria, then replan; unrelated features and new product direction remain outside automatic scope. |
| First batch or PR completes under continuous mode | Checkpoint and refresh the backlog, comments and checks; select the next ready batch rather than finishing the session. |
| Product decision plus independent ready bug | Record question/options/recommendation and affected work; fix the independent bug while the decision stays open. |
| Native/live/access/human verification missing | Record an external verification blocker and exact next action separately from product decisions; do not treat it as passing acceptance or close its delivery issue. |
| Project child sessions unavailable or repository reserves pushes for the manager | Report actual capability limits, preserve the chosen host, continue independent manager-owned work; follow verified ownership and never invent child commands or delegate forbidden pushes. |
| Continuous manager resumes after compaction | Recover durable queue, SHAs and task/issue/branch/PR/child mappings; inspect live worker and remote state before new work to avoid duplicate workers or mutations. |
| Fresh sweep has no ready tasks but unresolved holds | Report completed work and decisions/blockers precisely, preserve incomplete PRs/issues/parents, and give a continuation point. Do not claim the software is bug-free or all acceptance is delivered. |
| Hard session limit or repeated unchanged failure | Checkpoint unfinished work and move to independent tasks where possible; no fixed-cycle success claim, busy polling or blind unchanged retries. |
| `zdev -pr` | Explicit UI acceptance before plan; readable decisions and validated artifact ZIP when real files exist. |
| Standalone explicit GitHub management request | zgh may perform the requested operation; planning delegation never supplies that authority. |
| `-re` or newly reported sweep problem | Refresh only the handoff summary or add a local task during planning; tracking for accepted work is established later by the implementation agent. |
| Planning helper asked to publish resources | Return actual required files in the artifact ZIP; no resource PR, branch push or commit during planning. |
| No artifacts | State none required; give the complete standalone implementation prompt. |
| Indispensable exact asset unavailable | Name the dependent requirement and blocker; finish independent planning. |
| No `-m` | Implementation agent still creates/reuses tracking and records progress, but leaves the PR and delivery issues open pending integration with PR links and honest status. |
| `-m` with required check pending or red | Hold the affected PR and delivery issues open; record the exact gate and make no delivery claim. |
| `-m` with full acceptance, review, approvals, current-head checks | Merge per repository policy, confirm integration, add completion evidence, close fully satisfied children, then close the parent only when its entire accepted scope is complete. |
| Genuine non-code task | Close only after its explicit accepted deliverable and verification are complete; do not invent a code-merge requirement. |
| Partial implementation or merely replaced source issue | Keep remaining requirements visible and the issue open; creating a replacement or linking a PR does not establish completion. |
| Multi-PR `-m` with one eligible PR and one intentionally held PR | Merge only the eligible PR after its gates; retain the held PR, its incomplete issues and incomplete parent. State dependency order and each disposition in the prompt. |
| Task-specific user constraint | Honor it over generic defaults; choose a fitting workflow without needless orchestration. |
| Existing feature/resource PR | Inspect read-only and instruct the implementation session to reuse/update it when appropriate; distinguish merge from close-as-superseded. |
| Session creates deliverable files | Save each under one unique Dropbox `codex-artifacts/` session folder as produced, including prototype rounds and final ZIP; report actual upload status. |
| Dropbox unavailable or upload requires confirmation | Report the blocker or pending confirmation and provide available download fallback; never claim an upload succeeded. |
| zstatus/zwatch | Existing one-shot/ongoing observation behavior remains independent of planning. |
| `zkicadactions` plan request | Plan template filled with UNKNOWN where unestablished; separate authorities; no dispatch. |
| `zkicadactions` green identity receipt | Identity PASS only; connectivity, DRC, electrical, assembly and manufacturing reported NOT_EVALUATED; adoption left to the owner. |
| `zkicadactions` artifact download denied | Reported as unread evidence (UNKNOWN); no alternate tool, host or URL. |
| `zkicadactions` asked to upload a nonpublic candidate or auto-adopt routing | Held as unimplemented with its acceptance criteria; no upload or push. |
