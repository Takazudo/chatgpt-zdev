# Resource-only Work session

This mode preserves resources for an oversized Codex implementation. It authorizes only the handoff files, necessary scanner exclusions, and the branch/commit/push/draft-PR/issue updates needed to make them usable. Product implementation and merge are excluded, even if `-m` was carried for the eventual Codex work.

1. Read the accepted sibling-chat/issue context and inventory accessible resources. Persist original files where available; complete text/code may be materialized from readable context with source provenance and a reconstructed label. Do not require a ZIP, manifest, hashes, or generated verifier when the resources can be obtained this way. Preserve indispensable exact assets; request only those that cannot be recovered and continue persisting independent resources. Never claim regenerated or unavailable bytes are the accepted original. Do not bake adjacent scratch files or rejected variants unnecessarily.
2. Inspect the repository and resolve the parent and base topology from the issues. For one epic use its planned `base/<slug>`; for a super-epic verify or bootstrap its shared base from the recorded parent and use each epic's declared base. Check actual remote branch/PR state; reuse only this task's resources. Never overwrite unrelated branches.
3. Copy resources to `_temp-resource/<epic-number>-<slug>/`. This directory must be tracked while needed, not gitignored. Inspect the project's broad lint, format, typecheck, test-discovery and build scanners; add minimal exclusions where required so throwaway prototypes do not enter production scans. Do not weaken checks on product files. No dependency install or broad product test run is required just to persist inert reference files; validate the actual touched configuration and archive/source integrity.
4. Stage only these files and necessary exclusion plumbing, inspect the diff, commit and push. Open a **draft base PR** explicitly targeting the intended parent. Record its head SHA, exact paths, and hashes. Read back the remote bytes, compare them with the files actually persisted (and source hashes when available), and verify PR head/base. Record reconstructed resources separately from original transfers. Producer-local existence alone is insufficient.
5. Update each epic with **Use this PR as base**, the real branch/PR, pinned commit, resource directory, source manifest, and cleanup requirement. Update relevant sub-issues to read the resource from their working tree. Preserve every Super-epic marker and implementation-order section. Issues must not depend on a source session's local path or an expired sandbox URL.
6. For a super-epic, bake each epic's resources on its declared epic base targeting the shared super base. Record every resource PR and directory on the super-epic. Avoid unrelated resources on the final parent or duplicate common inputs; document ownership if common resources are necessary. The Codex receiver must reuse these prepared bases and rebase/merge earlier sibling changes as its established workflow requires, rather than branching from an unprepared default branch.
7. Leave all implementation issues open. Keep base branches and draft PRs for Codex. State explicitly: **resources persisted; product implementation not started**. A resource-only PR is not a completed feature and must not auto-close its implementation issue.
8. End with PR link(s) and a fenced Codex prompt containing: repository, full hierarchy/order, parent/base/head SHA, each resource PR/path/manifest, accepted decisions, verification evidence, actual merge permissions, and remaining work. Explicitly say to adopt the existing base PR(s), implement the full spec, move lasting source/tests/docs into their real homes, then delete `_temp-resource/<epic-number>-<slug>/` **before its implementation/root PR merges**. Keep generally useful scanner exclusions if appropriate. Apply [the portable Codex handoff contract](completion.md): no plugin skill invocations; explicitly list which base PRs to reuse/update, which PRs to keep or conditionally merge/close, and which issues close only after verified delivery, in child-to-parent order. No resource-only PR or implementation issue closes merely because resources were persisted.

If an artifact is oversized for ordinary Git, do not use Git LFS or secretly omit it. Keep it local/ignored and use an already authorized durable store that Codex can read, recording locator and hash. If no such route exists, give the exact missing-transfer instruction and mark the handoff blocked; finish independently transferable resources. If no repository or write access exists, preserve the complete ZIP and issue drafts and explain precisely what could not be persisted rather than claiming a PR exists.
