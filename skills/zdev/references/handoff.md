# Standalone implementation handoff

## Producer checklist

Complete the accepted implementation brief in readable Chat and prompt text: goal, accepted UI and corrections, behavior/states, constraints and non-goals, acceptance criteria, components, dependency order, verification and actual permissions. The current ChatGPT planning session and its delegated helpers perform read-only GitHub research. Do not create or change issues, epics, labels, comments, branches, commits or PRs, close or merge anything, or initiate GitHub-write approval requests here. Prepare the tracking structure and proposed issue content in the handoff. This session boundary does not restrict the separate implementation agent: require it to establish issue tracking before implementation, as specified in [implementation tracking](implementation-tracking.md).

Read current GitHub state before writing the prompt. Record actual issue and PR URLs, target branch and inspected SHA, existing bases/resources, checks already observed, and what is merely planned. Identify an existing matching tracker/epic and children for reuse when available; otherwise supply concrete titles, scope, acceptance criteria and dependencies for the implementing agent to create. Describe whether it should reuse/update a matching task PR or create a branch and draft PR. For multiple topics, give dependency order, integration checkpoints and explicit per-PR merge/hold decisions. Choose the simplest fitting implementation workflow. An explicit user restriction on new issues across implementation overrides the default: state the actual allowed tracking operations and adapt the template instead of emitting contradictory creation authority.

Follow [the artifact storage rules](artifact-storage.md) for session-created deliverable files and the ZIP. A ZIP is supplementary and contains real implementer-needed source/assets/fixtures when they exist; inspect and validate it. Otherwise state `Artifacts: none required`. Never imply that Chat attachments, sandbox paths or private previews are automatically accessible to another local or cloud session. Identify indispensable exact bytes and their destination-readable locator, or name the dependent blocker and continue independent planning.

Write for Codex or Claude Code in the user's chosen local or cloud environment. The prompt must stand alone with the accessible repository and identified inputs. Translate every accepted flag and workflow decision into ordinary actions: the accepted scope, accepted UI direction, dependency order, merge authorized or not, and exact completion gates. Keep normalized flags in producer-side notes only. Do not include `zdev`, `zplan`, `zproto`, `zgh`, `zudo-dev-flow`, `big-plan`, `x-wt-teams`, plugin/app links, private skill invocations, planner-only flags, or instructions to use a ChatGPT flow in the execution prompt. Do not describe the planning Chat or its permissions inside the prompt. A repository or artifact name that happens to match a skill name is factual data, not an invocation. Inline the relevant procedure instead of referring to a skill. Match available execution tools and models; do not require a particular host or unavailable orchestration.

Before delivery, read the complete generated prompt as a new implementing agent. Confirm that it can start tracking and implementation without this plugin, prior Chat history or unstated instructions; that it directs creation/reuse and ongoing updates of issues; and that no planning-only prohibition on issue creation remains. Check all user requirements and remove unresolved placeholders and inapplicable alternatives.

## Copyable prompt template

Replace every placeholder with actual information and omit inapplicable lines. Select exactly one merge-permission branch. Include one complete fenced text block in the final response; report saved files and link a real artifact ZIP separately when available. This template describes future work, not work already completed.

```text
Implement <accepted goal> in <repository URL>.
Execution environment: <the user's specified local or cloud environment; otherwise the current implementation session's available environment>.

Read repository instructions, <existing relevant issue/PR URLs, if any>, relevant comments and current source. Base: <branch>, last inspected at <SHA>. Refresh all state before changes.
Accepted scope: <complete requirements and accepted prototype decisions>.
Non-goals: <explicit exclusions>.
Acceptance criteria: <observable results>.
Tasks and dependency order: <each task's key, title, scope, affected components, acceptance criteria, verification and dependencies; include integration checkpoints>.
Execution strategy: <simple direct implementation or justified independent work groups, using tools and workers available in this session>.
PR plan: <each actual or planned PR, target, merge/hold decision, gate and issue effect>. Existing PRs/branches: <actual URLs, roles, states and SHAs, or none identified>. Reuse/update <matching PR URL when applicable>; avoid duplicate work.
Artifacts: <accessible repository paths or transferred files and exact-input needs, or none required>.
Verification already observed: <commands and results, CI revision, unknown/not-run checks>. Do not report a check as passed unless observed.

Before implementing, establish durable GitHub tracking for this accepted scope. Reuse <matching open tracker/epic and child URLs, if identified> after confirming its scope, and search for other matching open records before creating missing ones. For one focused task, use one tracker; for multiple independently completable tasks, create or reuse a parent epic plus linked sub-issues. This task authorizes creating, updating and closing these in-scope issues under the completion rules below; do not add a separate confirmation step for those already requested operations. Use this session's available authenticated GitHub tools and respect actual access controls. If a required write is unavailable, preserve the proposed issue content, report the exact blocker, and continue independent authorized work without claiming tracking was created.

Put the full accepted requirements, non-goals, decisions and rationale, target/base, dependencies, acceptance criteria, verification plan and artifact references in the tracker and relevant children. Map task keys to real issue URLs, link parent and children both ways, and use native sub-issue relationships when available; otherwise retain durable body links. Each task issue must be understandable without this conversation. Preserve existing context and original issues; do not close a source issue merely because another record references it.

Use those issues as the development notebook throughout the work. At meaningful milestones and before pausing or handing off, record findings, decisions or approach changes, completed and remaining work, test commands and observed results with relevant revisions, PR/commit links, blockers and the next action. Keep parent progress and child states consistent. Re-read changed issue bodies before editing and preserve others' content. Verify returned URLs and read back writes; after an uncertain response, inspect for an existing result before retrying.

Implement the accepted scope in dependency order, review the diff, run relevant checks and UI verification, fix change-related failures, push a branch, and open or update a draft PR targeting <branch>. Link its tracking issues. Inspect required CI for the current head and obey repository approvals and merge policy. Leave the PR draft while essential work or verification remains.
<If merge is not authorized: Leave implementation PRs open. Update each in-scope tracker, sub-issue and original issue with its PR link and actual implementation/verification status. Keep delivery issues open pending integration; do not merge or mark them delivered.>
<If merge is authorized: For each PR marked eligible, merge only after its accepted work, review, required approvals and current-head required checks pass under repository policy. Leave held or incomplete PRs open. Confirm integration into the intended target, add completion notes with PR and verification evidence, and close only issues whose own criteria are fully satisfied. Close completed children first; close their parent only when every accepted requirement and required child is complete. Preserve incomplete original issues, incomplete parents and unrelated issues. If any gate remains, hold that PR and record the exact blocker.>
For each existing dependency/resource PR, follow its stated disposition. Move lasting resources into production paths and remove temporary resource paths before merge. Never treat closing an unmerged PR or creating tracking records as delivery. Use non-closing issue references while required work or verification remains.
Merge authorization does not authorize deployment or a release. Report actual tracker/epic/sub-issue URLs and final states, PR states, verification, unresolved work and retained resources.
```
