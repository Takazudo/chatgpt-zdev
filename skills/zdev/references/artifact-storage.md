# Session artifact storage

Use artifact storage only when the plan includes useful deliverables beyond the copyable execution prompt. For a prompt-only plan, including an issue sweep or a lengthy plan expressed entirely as requirements, decisions and task instructions, deliver the complete prompt in Chat and state `Artifacts: none required`. Do not create or upload a duplicate prompt, brief, decisions log or plan file; create no Dropbox folder and request no Dropbox confirmation. Wrapping the prompt or its planning prose in Markdown, text or a ZIP does not make it an additional artifact. An explicit user request to save that text overrides this default.

When additional artifacts exist, save those files to the connected Dropbox under `/codex-artifacts/<session-folder>/`, including intermediate prototype source, accepted source, required assets, fixtures, useful screenshots and the final artifact ZIP when produced. Save them as they are produced, not only at the final handoff. Preserve useful relative paths and round names. Keep the complete prompt in Chat; do not upload a redundant prompt copy or include one in the ZIP merely because other artifacts exist. Upload accompanying notes only when they help use the actual files, not as a duplicate of the prompt. Do not upload transient scratch files, secrets, or unrelated user files. Respect any more specific user instruction.

Use the Dropbox connector and its applicable upload workflow; follow its confirmation, permission, file-type, conflict and size requirements. The user’s instruction to use this destination does not override a connector’s required confirmation. Create missing parent folders in order when authorized. Pick one descriptive, filesystem-safe session folder name with a date and unique suffix, check for collisions, and reuse it throughout this session; never overwrite another session or an existing file. When a file changes, use a distinct versioned name unless the available connector and user authorization explicitly permit replacement.

Upload the actual additional artifacts, retaining their extensions and bytes where supported. Create and validate the implementer ZIP when required by the handoff and upload it too; Dropbox storage supplements the complete prompt in Chat. Report the exact Dropbox folder and saved paths, and distinguish successful uploads from pending or failed ones. Do not claim success without a successful connector response. Do not create public or shared links unless requested.

If Dropbox is unavailable, permission or confirmation is pending, or a file cannot be uploaded, explain the specific blocker and provide the available Chat attachment/download as a fallback. Continue independent planning. Do not imply a Dropbox path is automatically accessible to a separate local or cloud implementation session: verify destination access, or identify the exact files and request transfer when indispensable. If no deliverable files exist, create no empty session folder and state `Artifacts: none required`.
