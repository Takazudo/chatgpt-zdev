# zdev workflow contract

## Chat plan to a standalone implementation session

The current ChatGPT planning session and every helper it delegates perform read-only GitHub research. Do not create or update issues, epics, labels, comments, branches or PRs; do not commit, push, close or merge, or initiate GitHub-write approval requests here. Return a self-contained prompt plus necessary artifacts. This is a session-specific boundary, not a prohibition on issue tracking by the separate implementing agent.

Plan in the current Chat with `zdev`. Inspect repository instructions, source, issues, PRs and base SHA. Resolve ordinary choices and record assumptions, dependencies, acceptance criteria, review and verification. Use stable local task keys while planning; identify matching existing issues and prepare concrete issue content without posting it. The user starts a separate Codex or Claude Code session, locally or in the cloud, with the final prompt. Chat does not claim to start or transform that session.

Require that implementing agent to establish tracking before changing implementation code: reuse or create one tracker for a focused task, or a parent epic plus linked sub-issues for multiple independently completable tasks. Include the full accepted requirements and keep meaningful decisions, progress, verification evidence, PR links, blockers and next actions in those issues throughout development. Close completed records according to their acceptance and integration requirements, children before parents. Follow [implementation tracking](implementation-tracking.md); issue creation is part of the requested execution, not an optional workaround or a new planning checkpoint.

Choose a fitting execution workflow. Big-plan and other orchestration patterns are design references only; the consumer need not know or install them. Simple cases need no artificial multi-PR topology. Task-specific user constraints override generic flag defaults. Match the user's environment, available tools and required platform verification.

Use `-pr` for a UI prototype and feedback loop. Show working variants when appropriate, preserve rounds, and wait for explicit acceptance before finalizing a direction. Put accepted behavior in readable Chat and prompt text. Supply a validated ZIP with complete accepted source/assets when these files exist. A ZIP supplements the specification; it is not an entry prerequisite unless the user requires exact bytes. Identify indispensable missing inputs and continue independent work.

Use `-is` for a bulk-checkpoint issue sweep, `-isask` for the per-candidate interview including previously postponed issues, or `-a` for an explicitly authorized continuous sweep. When sweep modes combine, `-isask` wins for the interview; otherwise `-a` supplies routine in-scope acceptance without another bulk checkpoint. Follow [the sweep procedure](issue-sweep.md). Neither `-m` nor routine autonomy skips an explicit interview or prototype acceptance. Without `-a`, preserve the normal `-is` bulk checkpoint.

For `-cccp`, target Claude Code Cloud's Project manager/child-session platform as described in [Project execution](claude-code-cloud-project.md). For `-a`, plan the first ready wave and a durable repeated loop as described in [continuous development](continuous-development.md). Keep these axes independent: selecting a Project does not start a sweep, and continuous development does not grant merge authority. An explicitly requested equivalent workflow in ordinary language has its stated meaning; do not silently infer additional flags or permissions.

## Flag and lifecycle contract

| Flag | Planning effect | Implementation handoff effect |
|---|---|---|
| no flag | Plan and record scope, dependencies, tracking structure, verification and permissions. | Establish/reuse tracking, implement and verify, keep issues updated, and leave the PR and delivery issues open pending integration. |
| `-m` / `--merge` | Record explicit conditional merge intent only. Planning never creates PRs or merges. | Establish/reuse tracking and keep it current. Merge eligible work only under repository policy after verification, review, approvals and current-head checks. Close fully completed children after confirmed integration, then eligible parents. No deployment or release authority. |
| `-is` / `--issuesweep` / `--issue-sweep` | Triage the requested backlog with a bulk checkpoint and named task groups. | Track and implement only the accepted scope in dependency order; reuse selected original issues and preserve unrelated coordination. |
| `-isask` / `--issue-sweep-ask` | Revisit postponed candidates with the interview checkpoint; wins over `-is`. | Same tracking and implementation lifecycle for accepted scope only. |
| `-pr` / `--prototype` | Iterate in Chat until the user accepts a UI direction; record decisions and artifacts. | Record and implement the accepted direction using repository architecture and verify its UI states. |
| `-cccp` (also written `- cccp`) | Select Claude Code Cloud Project as the destination and plan manager/child responsibilities from actual repository constraints. | A capable manager owns the queue, decisions, review and integration; use available child sessions for bounded independent work. No automatic sweep or merge authority. |
| `-a` | Inventory issues and PRs, distinguish current defects from landed fixes and acceptance holds, then provide the first ready wave and the continuous-loop contract. No redundant bulk approval for routine in-scope defects; an explicit interview still wins. | Repeat planning and development after each verified batch until a fresh sweep has no actionable in-scope work. Preserve decision and other blocker records. No automatic merge, deployment or release authority. |

Combinations compose: `zdev -m -is` performs a bulk sweep and carries conditional merge authority; `-isask -m -pr` interviews first, prototypes selected UI topics, then hands off accepted scope. `zdev -cccp -a -m` targets the Project manager/child team, keeps sweeping and fixing, and conditionally merges eligible work. `-cccp -a` keeps implementation PRs and delivery issues open pending integration. `-a -isask` interviews first and keeps unaccepted candidates held while continuing accepted work. Normalize the harmless spaced spelling `- cccp` to `-cccp`; explain other unknown flags instead of dropping them. Normalize flags in producer-side notes. In the final execution prompt, replace all flags with their plain-language scope and actions. Do not pass private commands, unsupported flags, plugin/app links, skill names or a requirement to invoke this workflow to the consumer.

The final prompt includes the actual repository URL and relevant existing issue URLs, target branch and inspected SHA, complete accepted scope and non-goals, task specifications and dependency order, tracking creation/reuse instructions, existing PR disposition, artifact access and exact-input needs, checks/current evidence and authorized lifecycle. Follow [the handoff rules](handoff.md). Keep the planning Chat and its permission boundary out of the execution prompt; its consumer needs only concrete instructions for its own session. Never invent issue IDs or URLs or claim future writes have already occurred.

## Implementation lifecycle carried by the prompt

Without merge authorization, open or update a reviewable PR, leave it open, and update each in-scope tracker, child and original issue with its PR URL and actual implementation/verification status. Delivery issues remain open pending integration.

With merge authorization, state a merge or hold decision for each PR. Merge only eligible in-scope PRs after accepted work, review, required approvals, current-head required CI and repository policy are satisfied. Intentionally held and incomplete PRs remain open; partial integration can be correct when the plan says so. Record remaining gates in the issues. Close only fully satisfied in-scope children after confirmed integration, then parents whose entire accepted scope is complete. Keep unresolved originals and unrelated issues open. Creating a tracker, preparing a prototype, opening a PR or closing an unmerged PR is not delivery. Merge authorization never grants deployment, release or plugin publication authority.

If a resource base PR already exists, inspect it and specify whether to adopt and update it; avoid duplicate PRs. Lasting files move into production locations and temporary resource paths are removed before merge. Link existing durable resources directly. Keep oversized generated files local/ignored; never use Git LFS. Do not infer permission to message people outside the requested GitHub workflow.

## Observation routes

`zstatus` is one read-only inventory; `zwatch` observes active Codex/Claude Code runs for the user-requested lifetime through available supervised execution. Follow [the observation contract](../../zstatus/references/observation.md) and [watch lifecycle](../../zwatch/SKILL.md). These are independent of planning and grant no authority to answer agent questions or resume agents.
